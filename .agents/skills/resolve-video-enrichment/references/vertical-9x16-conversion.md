# Horizontal 16:9 → vertical 9:16 split-screen conversion (Resolve scripting)

Load only when the user explicitly authorizes reformatting existing finished 16:9 timelines into `<OriginalName>_9x16` variants. Conversion is never implied by enrichment or framing work; originals stay read-only.

## Procedure
1. **Back up and baseline first.** Verified `.drp` export, then a JSON baseline of every original (id, raster, start/end, FPS, track counts, subtitle cue text + absolute frames). Re-compare originals against it live before the pilot and after the batch.
2. **Read-only preflight.** Record version, active timeline id/timecode, page, project vs per-timeline FPS, and the existing `_9x16` timelines with every item's transform props and Fusion Transform inputs. Resume work from live state, not from agent handoff files.
3. **Calibrate on the real build before choosing numbers.** On the pilot `_9x16` only: disable the other video tracks (`SetTrackEnable`, ~1.2s apart), set one property at a time (floats), export a still, and measure the non-black bounding box with numpy. Restore the item's saved properties and every track-enable state in a `finally`. Run one variable per probe and read the property back after each set.
4. **Derive the layout from the measurements** (keep it in one module so the pilot script, batch script and verifier share it). Measured on 21.1.0.17 for a 1920x1080 source on 1080x1920: `fit = min(W/w, H/h)` = 0.5625; Zoom multiplies fit; Pan moves 1 canvas px per unit (+ right); Tilt moves `fitted_h/canvas_h` ≈ 0.316 canvas px per unit (+ up); Crop values are canvas px at Zoom 1 (on-canvas size scales with Zoom) and apply before Pan/Tilt.
5. **Pilot layout.** V1 = game in the top panel (zoom to fill the panel, pan so the facecam region is excluded, crop the source's letterbox bar edge); V2 = the same stream zoomed/cropped to the facecam region in the bottom panel, with `CropTop` hiding game pixels above the panel and headroom kept above the head; V3 Adjustment Clips = Fusion Transform (`Size` ≈ 2, `Pivot` at the lower-panel centre e.g. (0.5, 0.25), `Center` (0.5, 0.5)) so the lower panel fills the canvas; V4 GIFs keep timing and are moved clear of the face and the caption zone. Facecam position/size is per-channel and per-stream — export one clean full-resolution still per distinct V1 source file (group timelines by source clip name) and read the eye-midpoint x / eye y off a gridded crop. Derive each stream's lower-panel scale from `(canvas_h - target_eye_y) / (src_h - eye_y)` so the eyes land on the pilot's eye line on every stream; that keeps the fixed-pivot Fusion focus zoom framed like the approved pilot. One scale for all streams cut the head or left a huge empty headroom on streams whose facecam sits higher or lower.
6. **Verify with independent evidence.** Export stills at a normal frame, a GIF frame and a V3 focus frame; run a pixel check (1080x1920, no pure-black void, avatar present in the lower panel). Define a black row by the row MAX (<~16), not the row mean, and only fail it where the avatar always sits (lower panel below its headroom, e.g. canvas y>=1300): dark game scenes (night, boss arenas) legitimately darken the top panel and the headroom band, and a mean-based test false-failed a Terraria timeline. Report heavy top-panel darkness for a visual look instead of failing it and look at the images (crop the top panel at full resolution to check the seam and facecam bleed). Compare subtitle text/frames, audio items, V1 ranges, duration, FPS and offline state against the live original, then `SaveProject()` and restore timeline/timecode/page.
7. **Stop for user approval of the pilot** before any batch. Then go one timeline at a time, resolving by id + exact name, with per-timeline verification and a hard stop on the first anomaly. Inspect each batch item's stills — a framing formula tuned on one clip does not prove the others — and handle non-60fps timelines separately.
8. **Batch mechanics.** Keep one converter that does duplicate → raster → V4 GIFs → V2 panel → transforms → verify → save for a single index, appends per-timeline results to a JSON file, and returns non-zero on the first failed check. Run only ~2–3 timelines per terminal call (each takes ~20s with 1.2s spacing) so the call stays well under the tool timeout, and do not chain several batches inside one call. Resolve went `Not Responding` twice after roughly 10 consecutive duplicate+edit cycles in a session, even with 3-per-call batches and short pauses, so treat the cumulative count as the risk: after ~8 timelines stop, let Resolve idle, and if it is stuck ask the user to restart it before continuing. Resume from the results file plus a live read-only preflight, never from the last log line. A hang mid-timeline leaves a half-built `_9x16` (raster still 1080x1080 / 3 video tracks): after Resolve recovers, delete only that timeline by exact name + id + wrong raster (refuse if it already looks complete), save, then re-verify every finished timeline against its original before resuming.

## Pitfalls
- Appending a GIF with its source range read back from the original (`GetSourceEndFrame`) can return one frame short when the GIF plays to its last frame (43-frame GIF came back 0..41). Pass `endFrame = src_end + 1` when `src_end >= Frames - 1`, then compare record start/end and source start/end against the original for every GIF.
- A long multi-timeline run in one terminal call that hits the tool timeout leaves the Python children running against Resolve and can coincide with Resolve going `Not Responding` (window title shows it; `Process.Responding` is False; CPU nearly flat). Kill only your own stuck Python processes (match them by command line so queued edits cannot fire on recovery), do not click or send the Problem Report, and do not force-close Resolve without the user's say-so. One hang cleared by itself after a few minutes; the next had not after 4+, so report it and let the user decide. Resume only after a read-only check for a half-built `_9x16` timeline.
- Bash `-Command` strings mangle PowerShell `$_`; write a `.ps1` file and run it with `powershell -File` for process/window inspection. `ImageGrab` screenshots may capture the terminal instead of Resolve, so they cannot diagnose a Resolve dialog.
- A verifier that only compares the numbers the script itself set (or checks file size) certifies nothing; a bad layout (black void, decapitated avatar, off-screen focus) passed such a check. Gate on measured pixels plus a visual review.
- Guessing Crop/Tilt values from the Inspector without calibration produced a large black void and a cropped head; measure first.
- A scripted still export has no subtitles; subtitle-vs-avatar overlap needs a viewer capture of Resolve itself (an OS screenshot may capture another window), so report it as unverified until seen.
- On 21.1.0.17 reads of an INACTIVE timeline depend on the active one: Pan/Tilt/CropTop come back scaled by the raster ratio (a 9:16 timeline read while a 16:9 one is active gave Pan x1.778, Tilt /1.778), track enable/lock flags read False, and audio GetProperty omits default keys. Compare signatures only when read under the same conditions — activate the timeline being read (`p2_9x16_convert.read_protected` / `stable_sig`). A "diff" on the approved pilot was this quirk, not an edit.
- A deep-blue hair-colour mask false-failed on blue game scenery in the lower panel. Gate the layout instead by rebuilding the expected 9:16 frame from a clean ffmpeg source frame with the stream anchors (and the Fusion focus affine: scale about Pivot, offset by Center-0.5) and comparing it to Resolve's still (`p2_9x16_convert.expected_canvas`; good = corr ~0.999, MAD ~2; a wrong anchor scores corr ~0).
- Keep docstrings, constants and verification thresholds in one module; a script whose docstring and code disagree sends the next agent down the wrong path.

## Verified run: day 24 reuse of the day-22 builder (21.1.0.17)

For a second timeline of the same channel layout (2560x1440 source, avatar baked bottom-right, letterbox rows 26..693 of 720, avatar x ~935..1210) the day-22 geometry was reused unchanged after measuring the same landmarks (black bar start 0.9625, ahoge ~0.569).
- Copy `scripts/build_9x16_day22.py` to `build_9x16_dayNN.py` and change only `ORIG_NAME`, `OUT` and the log name; the builder asserts 3 video tracks, a single V1 clip and V2 made only of Adjustment Clips, so a timeline with a different track set fails fast.
- Dry run first (it prints the plan without writing), then `--apply`. Result: `<name>_9x16` at 1080x1920 with `Game Top` / `REACTIONS` (GIFs, original frames) / `VTuber Bottom` / `VTuber Full` (the 7 focus ranges as full-screen avatar); protected audio/subtitle/V1 signatures equal; original stays 1920x1080 with 3/3/1 tracks.
- Pixel review: 5 stills (normal, full-screen focus, 2 GIF frames) showed no black band and the ahoge/face inside. Only 1 of 7 focus ranges was viewed; subtitle overlap with the avatar is unverified because scripted stills omit subtitles.

## Illustrated-overlay clips (Armigon layout B, verified 2026-10-31)

- Build from the live illustrated timeline, not the original `placements.json`: the user may trim, split or delete reel pieces and add stills. Map each live reel item to its placement by `GetLeftOffset()` inside `[sourceStart, sourceEnd)`; rebuild only the full-frame art that is still on the timeline.
- A square still (3000x3000) in a 1080x1920 timeline with `scaleToFit` fills the width; Tilt is in units of fitted-height/canvas-height (1080/1920 canvas px). Centre in the top band: `Tilt = (960 - band/2) / 0.5625`, `Zoom = target_px / 1080`. Confirmed by a rendered Resolve frame (logo centred in the band).
- Full-frame 16:9 art with titles needs a 1080x1920 HyperFrames reel (text cut otherwise); keep the same text/animation and timings. Scripts: `scripts/scratch/armigon_whyvtuber_9x16_plan.py`, `build_armigon_whyvtuber_art916.py`, `armigon_whyvtuber_9x16.py`.
