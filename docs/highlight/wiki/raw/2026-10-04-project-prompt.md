## หลักการ: ห้ามฝังข้อมูลไว้ตายตัว

- ห้ามเชื่อรายการไฟล์ ความยาว codec จำนวนไฟล์ หรือ `clip_id` ที่เคยเห็นในงานเก่า ทุกอย่างต้องอ่านสดจาก `INPUT_DIR` และ Resolve ทุกครั้งที่เริ่มงาน
- `INPUT_DIR` เปลี่ยนได้ทุกงาน และมีกี่ไฟล์ก็ได้ ประเภท `.mp4`, `.mkv`, `.mov`, `.webm`, `.ts`, `.m4v` (ไม่ลงโฟลเดอร์ย่อยเว้นแต่ผู้ใช้สั่ง)
- `source_id`: สร้างอัตโนมัติเรียงตามชื่อไฟล์ เป็น `v01`, `v02`, ... บันทึกการแมปชื่อไฟล์เดิมใน `WORK_DIR/inventory.json` ห้ามใช้การจับสตริงในชื่อไฟล์แบบฝังโค้ด (แผนเดิมที่ใช้ `HBD`/`Backrooms` ฯลฯ ถือว่าถูกแทนที่ด้วยข้อนี้)
- ชื่อไฟล์อาจมีอักขระพิเศษ (`【】`, ภาษาไทย, `｜`, `⧸`) ให้หาเส้นทางผ่าน `pathlib.Path.glob` ส่งให้ `subprocess` เป็นลิสต์ ไม่ใช้ shell เปิดไฟล์ข้อความด้วย `encoding="utf-8"`
- ความยาว fps codec อ่านจาก `ffprobe` ลง `inventory.json` เท่านั้น ถ้า fps แต่ละไฟล์ไม่เท่ากัน ให้แจ้งผู้ใช้ก่อนสร้าง Timeline (กฎ mixed-fps ใน `resolve-rough-cut`)

## Resolve

- ตรวจสดก่อน: `resolve_control runtime_mode`, `project_manager get_current`, `project_manager list`, `project_manager snapshot`
- ถ้าโปรเจกต์ที่เปิดอยู่ชื่อ `JOB` และมีฟุตเทจใน Media Pool ตรงกับ `INPUT_DIR` ให้ใช้ต่อ ไม่สร้างใหม่ ไม่นำเข้าซ้ำ
- ถ้าเป็นงานใหม่ (ไม่มีโปรเจกต์ หรือฟุตเทจไม่ตรง): ตามกฎ `resolve-rough-cut` ถามผู้ใช้ว่าจะเพิ่ม Timeline ในโปรเจกต์ซีรีส์เดิมหรือสร้างใหม่ ตั้ง `timelineFrameRate` ให้ตรง fps ฟุตเทจก่อนมี Timeline อันแรก แล้วสร้างโฟลเดอร์ชื่อ `JOB` ตั้งเป็น current folder ก่อนนำเข้า
- ห้ามสลับ/ปิดโปรเจกต์ที่มีงานยังไม่บันทึกโดยไม่ถามผู้ใช้
- Playback frame rate ตั้งผ่าน API ไม่ได้: ให้ผู้ใช้ยืนยันเองที่ Project Settings (ไอคอนเฟืองมุมขวาล่าง) -> Master Settings -> Playback frame rate ห้ามเดาเมนูอื่นเพิ่ม
- ตรวจสถานะ offline ของคลิป (โดยเฉพาะ AV1) ก่อนสร้าง Timeline ถ้า offline ให้ถามผู้ใช้ก่อนทำ proxy H.264

## ข้อกำหนดที่ห้ามละเมิด

- `INPUT_DIR` อ่านอย่างเดียว ห้ามเขียน แปลงไฟล์ หรือลบ ผลงานทั้งหมดอยู่ใน `WORK_DIR`

- ตาม `house-style`: Timeline เป็นการ assembly เท่านั้น ห้ามใส่ title, caption, text card, transition, effect, speed ramp, เพลง หรือ grading เว้นแต่ผู้ใช้สั่ง
- งานยาว (คัดช่วง ถอดเสียง) รันเป็น background process แบบ `notify=true`
- TDD ทุก Task ที่เป็นโค้ด และ commit บ่อย
- ถ้าขั้นไหนล้มเหลว ให้บอกตรงๆ ห้ามแต่งผลลัพธ์แทน
